## 1. 项目起因与原始设想

用户曾在串串店结账时，看到服务员使用手机或类似设备扫描签束，自动得到竹签根数。用户希望实现类似能力，并通过小程序提供服务，让使用者通过微信搜索或扫码即可使用普通手机拍摄，无需购买专门的数签设备。

最初提出的模型方向：

- 重点探索 VLX-Seek 10B。
- 前期可采用 Qwen3-VL-2B（MLX 4bit）进行本地验证。
- 最终生产引擎需要根据真实场景中的准确性、耗时和成本确定。

参考照片：`Snipaste_2026-10-16_12-31-01.png`。

照片展示的是一束竹签的端面，为本项目明确了识别目标：逐个定位可见签头，再统计实例数量。该图片仅作为场景参考，本轮未开展逐根标注，也未运行指定模型进行计数验证。

用户最初希望讨论的六个方面：

1. 目标用户与背景。
2. 需求设计方案与原型。
3. 技术方案、技术选型与项目架构。
4. UI 设计方案。
5. 实施计划与研发周期。
6. 市面同类能力及成熟经验。

用户最初要求先讨论、不输出文件；本轮结束时，用户明确要求先将讨论过程和结果整理成 Markdown，后续继续讨论。

### 2.1 已确认的方向

- 第一版主要服务串串店店员结账数签。
- 使用普通手机，通过微信小程序提供入口。
- 门店自行设置价格；模型专注视觉识别与数量相关输出。
- 采用逐根位置标记与人工修正，使结果能够复核。
- 支持同一桌多把签累计，区分“重拍当前把”和“新增一把”。
- 保存自动结果、最终确认结果及结账所用单价。
- 首版对象先收敛到圆形竹签端面。
- 前期先验证现有模型效果，训练根据评测结果安排。

### 2.2 尚未确定的事项

- 最终生产模型，以及是否需要专用签头模型。
- 数量范围、拍摄规范和准确性验收门槛。
- 真实门店样本是否可取得、能覆盖多少场景。
- 店员登录、门店管理和权限的具体设计。
- 上线部署环境、并发量和成本预算。
- 高保真原型、最终 UI 样式及正式研发排期。

## 3. 产品定位、用户与范围

### 3.1 产品定位

面向串串店店员的拍照数签与结账辅助工具。

核心目标：

- 减少人工清点耗时。
- 让每根签的识别结果能够被检查和修正。
- 为数量确认和结账核对保留依据。

### 3.2 用户分层

| 用户 | 主要诉求 | 当前定位 |
| --- | --- | --- |
| 门店店员 | 快速完成数签、修正和确认 | 第一版核心用户 |
| 门店老板 | 设置单价、查看清点与结账记录 | 第一版相关管理角色，具体权限待定 |
| 普通顾客 | 自行核对数量、查看计数依据 | 后续可扩展，不作为第一版验收主场景 |
| 连锁管理者 | 多店管理、统一流程、异常分析 | 后续讨论 |

### 3.3 首版功能范围

| 功能 | 当前方案 |
| --- | --- |
| 拍照与选图 | 拍摄竹签端面，也可从相册选择图片 |
| 拍摄引导 | 展示签尾对齐、完整入镜、保持清晰的示例 |
| 自动识别 | 输出签头点位或边框，程序统计有效实例数量 |
| 人工修正 | 支持放大、补点、删点、撤销，数量随修改更新 |
| 多批次汇总 | 同一桌可清点多把签，汇总已确认批次 |
| 门店计价 | 门店配置计价组及单价，店员选择组别 |
| 金额计算 | 按确认根数与对应单价计算 |
| 记录保存 | 保存原图、标记结果、自动数量、最终数量及单价快照 |

正式支付、收银系统对接、多门店复杂权限，以及多种物品计数，留待后续单独确定。

## 4. 业务流程与关键规则

### 4.1 核心流程

1. 店员打开小程序，进入本桌清点任务。
2. 选择计价组；如果门店只有一种单价，可采用默认组。
3. 整理签束，使签尾尽量对齐，拍摄清晰照片。
4. 系统识别并逐根标记，显示自动数量。
5. 店员放大检查，必要时补点、删点或重拍。
6. 店员确认当前批次数量。
7. 继续新增一把，或完成整桌汇总。
8. 程序计算金额，保存数量与结账记录。

“本桌清点任务”采用桌号还是临时记录编号，后续继续确定。

### 4.2 职责划分

| 环节 | 负责内容 |
| --- | --- |
| 视觉识别引擎 | 定位签头，输出对应实例 |
| 计数程序 | 按有效实例统计数量，处理人工修改后的汇总 |
| 门店 | 设置计价组与单价 |
| 店员 | 选择组别、检查标记、确认数量 |
| 计价程序 | 使用确认数量和当次单价计算金额 |

### 4.3 新增与重拍

- “新增一把”：创建新批次，确认后加入整桌合计。
- “重拍当前把”：替换当前批次的识别结果，保留批次归属。
- 同一把签的多张重拍照片不能被作为多个独立批次重复累计。

说明性示例：

| 操作 | 第一把 | 第二把 | 合计 |
| --- | ---: | ---: | ---: |
| 两把均确认 | 84 | 76 | 160 |
| 第二把重拍并确认 | 84 | 75 | 159 |

以上数字仅用于解释规则，与参考图片的真实根数无关。

### 4.4 多种单价

门店可设置“普通签”“大签”等计价组。如果不同组单价不同，由店员分组拍摄并选择对应组别。

第一版先采用人工选择组别，让识别模型集中解决签头定位和计数。未来自动分类是否有必要，根据实际门店需求决定。

### 4.5 确认与留档

- 自动数量与最终确认数量分别保存。
- 人工修改保留与原识别结果的对应关系。
- 单价保存当次快照，后续改价不会影响历史记录。
- 可见签头严重模糊、出框或完全遮挡时，引导整理签束、重拍或分批清点。
- 店员确认结果作为本次结账数量依据。

## 5. 需求原型与 UI 方向

当前形成的是文字原型，尚未绘制高保真页面或完成真机交互验证。

### 5.1 页面组成

| 页面 | 主要内容 | 关键动作 |
| --- | --- | --- |
| 首页 | 拍照数签入口、相册入口、拍摄示例、最近记录 | 开始清点 |
| 拍摄页 | 取景区域、签尾对齐与完整入镜提示 | 拍照、重拍 |
| 结果复核页 | 原图、签头标记、自动数量、当前数量 | 缩放、补点、删点、撤销、确认 |
| 整桌汇总页 | 各批次数量、计价组、单价、合计金额 | 新增一把、重拍某批次、完成保存 |
| 历史记录页 | 时间、原图与标记、数量、单价及金额 | 查看核对 |
| 门店设置页 | 计价组、单价等配置 | 设置和修改价格 |

### 5.2 视觉建议

- 使用暖白背景、深色文字、橙色主按钮，突出工具操作。
- 结果页优先展示照片和数量。
- 签头采用与竹签颜色对比明显的小点或细框，避免遮挡目标。
- 支持编号开关、双指缩放及局部放大，便于密集区域复核。
- 主操作按钮适合店员单手点击。
- 数量修改后立即更新，并清楚显示当前是否已确认。

以上为设计建议，配色、控件和页面布局仍需继续讨论。

## 6. 技术路线、选型与项目架构

### 6.1 模型路线对比

| 路线 | 当前用途 | 重点验证问题 |
| --- | --- | --- |
| Qwen3-VL-2B，MLX 4bit | 前期本地实验、识别基线、交互验证 | 密集小目标定位、漏检与重复、输出稳定性 |
| VLX-Seek 1.5-10B | 重点验证定位与计数路线 | 候选区域召回、区域匹配、推理速度与成本 |
| 专用签头检测或点定位模型 | 生产方案候选 | 标注投入、跨门店稳定性、独立计数效果 |

Qwen 2B 的表现不能代表 VLX-Seek 10B；各路线应使用同一批独立测试照片比较。

生产引擎按准确性、复核工作量、端到端延迟和单次成本选择。目前未确定最终生产模型。

### 6.2 已查证的模型相关信息

- Qwen3-VL-2B 已有 MLX 社区的 4bit 权重，可通过 mlx-vlm 实验。[3][4]
- VLX-Seek 官方提供定位、计数等区域相关能力，支持传入自定义候选框。[1][2]
- VLX-Seek 开源实现使用 WeDetect 替代未公开的内部 OPN；需要验证开源流程在本场景中的实际效果。[1]
- 当前 VLX-Seek 推理文档说明默认生成 100 个候选框；密集签束应专门检查候选框数量和召回情况。[2]
- VLX-Seek 官方主要测试平台为 Linux，并推荐 GPU。[1]
- MLX-VLM 提供 LoRA、QLoRA 等训练支持；所选模型、量化配置与设备的训练兼容性仍需实测。[5]

上述信息于本轮讨论中查询，仅说明工具或模型具备相关入口，不代表本项目已经达到实际结账要求。

### 6.3 需要重点验证的工程问题

- 签头过小、相互贴近时，是否能完整定位。
- 阴影、反光、断签和手部背景是否产生误检。
- 候选框、结果去重和图像切片是否导致漏数或重复数。
- 点位映射到手机显示图、缩放图后，是否仍准确。
- 自动识别的提升是否足以降低店员的实际复核时间。
- 单个模型的推理速度、内存和并发能力。

候选生成已漏掉的签头，应优先改善候选召回；完全不可见的端面需要通过调整拍摄方式取得信息。

### 6.4 初步技术选型

| 模块 | 建议方案 | 状态 |
| --- | --- | --- |
| 微信端 | 原生小程序 + TypeScript | 初步建议 |
| 业务接口 | Python + FastAPI | 初步建议 |
| 图像处理 | OpenCV，用于裁剪、清晰度检查等 | 初步建议 |
| Mac 实验引擎 | mlx-vlm + Qwen3-VL-2B MLX 4bit | 拟验证 |
| VLX 实验引擎 | 独立 VLX-Seek 推理服务，评估 GPU 部署 | 拟验证 |
| 数据存储 | POC 采用 SQLite；试点阶段再考虑 PostgreSQL | 初步建议 |
| 图片存储 | 本地实验目录；试点阶段采用对象存储 | 初步建议 |

用户端通过网络调用后端识别服务。普通手机无需运行 10B 模型；开发机与正式服务环境分开规划。

### 6.5 仓库划分建议

采用单仓库，将以下职责分开维护：

| 目录示例 | 职责 |
| --- | --- |
| `apps/miniapp/` | 小程序页面、拍摄、点位编辑、批次汇总 |
| `services/api/` | 门店配置、任务、记录与计价接口 |
| `engines/` | Qwen、VLX-Seek、专用模型的适配实现 |
| `contracts/` | 共用的识别结果与业务数据约定 |
| `evaluation/` | 评测脚本、结果对比与错误分析 |
| `docs/` | 需求、设计、操作规范和评测结论 |

该结构是建议方案，本轮尚未创建代码仓库。

### 6.6 识别输出约定的方向

统一识别结果应能表达：

- 签头点位或边框及其坐标约定。
- 自动计数结果。
- 照片质量检查和需要复核的原因。
- 使用的识别引擎与模型版本。

业务层另外保存人工修改、最终确认数量、批次归属和价格快照。具体字段、接口和坐标格式待后续技术设计确定。

## 7. 是否需要图片训练

### 7.1 当前结论

预留数据积累和模型训练的能力，第一步先用现有模型评测。是否训练、训练哪一层，由错误分析决定。

日常上传图片进行识别属于推理，模型参数保持不变。训练是单独的数据处理与模型更新过程，经评测后发布新版本。

### 7.2 分阶段路径

| 阶段 | 主要工作 | 训练安排 |
| --- | --- | --- |
| 初步 POC | 使用现有模型识别真实照片，建立基线 | 暂不训练 |
| 专项优化 | 改进拍摄、预处理或签头检测 | 按需训练检测或点定位模型 |
| 大模型微调 | 处理候选区域已较完整、但语义选择仍持续出错等问题 | 单独评估微调收益和资源 |

按 VLX-Seek 的区域处理结构判断，若候选阶段持续漏掉签头，应优先改善或训练候选检测器。[1]

若专用签头模型已经能稳定定位并计数，还应比较它独立运行与结合 VLM 的效果和成本。

### 7.3 训练数据要求

| 数据 | 用途 |
| --- | --- |
| 真实原图 | 覆盖不同手机、光线、数量、背景与签尾状态 |
| 每根签头的位置标注 | 为检测或点定位提供直接监督 |
| 人工核实根数 | 检查标注和最终计数是否一致 |
| 错误样本及原因 | 有针对性补充训练或改进拍摄 |
| 独立验证、测试数据 | 选择模型与检验泛化效果 |

选用目标检测模型时标注边框；选用点定位模型时标注中心点。仅有整张图片的总数，无法提供逐根定位的直接监督。检测框架的自定义数据集准备可参考官方资料。[8]

店员修正过的点位可作为候选标注，经复核后再用于训练。

### 7.4 样本量与数据划分

- 首轮计划采集约 100～200 张真实照片，用于发现问题和建立评测基线。
- 这一数量不是训练充分性的保证。
- 后续根据错误类型、场景覆盖和试验结果追加样本。
- 按签束或门店隔离训练、验证与测试数据。
- 同一束签的相似连拍图片不能跨集合混用。
- 训练数量和预算应在第一轮评测之后确定。

### 7.5 训练资源

MLX-VLM 提供轻量微调入口，但推理可运行不等于同设备能够完成所选训练配置。[5]

图像分辨率、批大小、可训练模块和优化器等都会影响训练资源需求。用户当前实际用于本项目的开发设备、可用 GPU 和预算尚未确认，因此本轮未承诺具体训练配置或成本。

## 8. POC 验证与验收方向

POC 要验证“拍摄规范 + 识别引擎 + 人工复核”的整体流程。

### 8.1 样本覆盖

建议覆盖：

- 少量、中量和密集签束。
- 自然光、室内灯光、较暗和明显阴影。
- 不同拍摄角度、距离和背景。
- 签尾整齐与参差不齐。
- 不同手机。
- 粘连、断签和其他干扰。

真实门店及人工核实样本的可获得性仍待确认。

### 8.2 评测指标

| 指标 | 关注点 |
| --- | --- |
| 整图根数完全正确率 | 一张照片是否数对全部根数 |
| 逐根定位情况 | 漏检、误检、重复检测分别是多少 |
| 人工修正次数与耗时 | 店员实际需要付出多少复核工作 |
| 重拍与拒识比例 | 有多少照片无法直接用于确认 |
| 端到端耗时 | 从上传到结果显示所需时间 |
| 整桌清点耗时 | 从整理签束到确认总数所需时间 |
| 单次识别成本 | 推理、存储、带宽等资源消耗 |

仅看总数可能掩盖“漏数与重复数恰好抵消”的情况，因此总数与逐根标记应同时检查。

具体准确率门槛、允许修正次数、数量上限及延迟目标，后续根据真实业务和基线结果确定。本轮没有实测指标。
