# 数得快：研发推进计划与周期

版本 v0.3｜2026-10-16｜试点与商业化分开估算｜[入口](../README.md)

## 1. 估算前提

1 名熟练全栈开发配合 AI；门店负责人配合业务决策和试用；样本采集、实物核实与批量标注有专人或额外工时。已有可用 Mac，VLX 阶段能取得经验证适用的 GPU 环境。具体配置和费用尚未确认。

本计划是“可试点并完成受控验收”的规划，不承诺公开上线日期。D0 表示真实启动日，不使用文档日期假设已经开工。

G0 首批建议至少 30 张可核实的实物照片，用于冒烟与问题发现；随后积累 100～200 张探索样本。只有自建场景可继续实验，但真实门店样本仍是 G4／G5 的前置条件。

G1 不要求 Qwen 先证明 VLX 能达 98%；若 Qwen 不能稳定输出点位，允许保留业务原型与评测工具，暂停围绕该引擎做无证据优化。VLX 效果在 S4 独立验证。

若 G1 连“可复核定位、可操作拍摄、合理纠错负担”都没有可行证据，不直接投入完整 S2／S3。先用 S4 中最小适配实验提前查明 VLX 路径是否可行，再决定继续投入；任务工时只挪动顺序，不重复计算。正常情况下仍按既定路线先 Qwen 验证、上线前 VLX 正式验收。

## 3. 周期与资源

基线 39 人日 + 风险预算 8 人日 = **47 人日**。风险预算用于环境联调、真机差异、识别输出修复和有界返工，不预先安排额外功能。

单人执行的建议窗口：

| 时间窗 | 重点 |
| --- | --- |
| 第 1～2 周 | 契约、样本规则、Qwen POC、原型走查，启动业务骨架 |
| 第 3～4 周 | 业务、图片、任务、版本与完成事务 |
| 第 5～6 周 | 小程序拍摄、点位编辑、汇总与恢复 |
| 第 7～8 周 | VLX 环境与评测、端到端、压测与发布核验 |
| 第 9～11 周 | 门店观察、问题修复、回归、缓冲与移交 |

预计 **约 10～11 周**。试点建议至少观察 10 个营业日，T23／T24 只计算开发修复和移交工时；观察中的非开发等待与其他检查尽量交叉安排。47 人日不等于连续 47 天日历时间。

外部样本、标注、GPU 采购／租用、主体与域名等等待不计入上述净工时。正式排期在 G1 和 G3 各重新估算一次，原 v0.1 的 5～9 周只作为历史粗估保留。

## 4. 数据工作量单列

T02 的 1.5 人日只包含规范、manifest 校验及标注质量检查流程，不包含整批采集和逐根标注。

正式测试建议准备至少 500 张独立照片，覆盖至少 3 家门店、3 类手机及不同数量／光线。该规模为设计建议，需冻结后执行；只有一家门店时只能形成该门店范围内的受控结论。

标注工时按实际计时计算：图片数 × 每张采集后核对与标注分钟数 ÷ 60。例如每张 4～8 分钟，500 张约 33～67 小时，约 4～8 人日；这是估算情境，实物采集和人工清点另计。若全部由同一开发者承担，应额外增加约 1～2 周或按实测重排。

## 5. 依赖与可交叉工作

关键路径：T01 → T03／T04 → T06～T12 → T13～T16 → T18／T19 → T20～T23。

在接口稳定后，采集与标注可以与研发交叉；原型走查可与 Qwen 评测交叉；GPU 资源准备应在 S0 启动。单人执行不能把两个开发任务的工时当作同时完成。

若增加一名前端开发，S2／S3 可在契约冻结后交叉；不得直接将总周期除以二，因为点位映射、异常恢复和端到端测试仍有依赖。

## 6. 决策触发与停止条件

| 触发 | 动作 |
| --- | --- |
| 没有真实门店照片 | 继续自建 POC；G4／G5 不通过，不声称可以真实结账 |
| Qwen 只能报总数或格式不稳定 | 记录失败类型；验证提示／解析最小改动，最多安排一次有界复测 |
| 候选召回不足 | 改拍摄／候选生成；单列检测训练，不把问题归结为语言提示 |
| VLX 支持范围或耗时达不到目标 | 限定受控范围、继续优化或重排；不降低既定验收口径掩盖失败 |
| 复核时间高于人工基线 | 先调整拍摄与复核流程，再评估算法投入 |
| 需要至少 200 个候选区域 | 保留为后续优化；另估多轮、切片或模型扩展成本 |
| 跨店、手机或灯光明显退化 | 扩充对应样本，限制试点范围，重新独立测试 |

训练、200 区域扩容、收银对接不包含在 39 人日中。立项时应新增独立任务、数据／资源预算和验收集。

## 7. 每阶段可评审交付

阶段报告必须包含版本、环境、输入数据清单、执行方法、实际结果、未通过项与下一步决定；不得只提交“已完成”状态。

POC 看事实与错误样本，研发看可运行流程和测试，试点看店员独立任务与整桌数据。新发现引起的范围变化先回写 00、01、03，再调整 05 与 06。

## 8. 商业化增量：已纳入分阶段规划

原39人日＋8人日只覆盖受控清点试点，不能解释为完整收费平台。用户已确认面向多家独立门店收费，按08～11补齐以下工作，作为G6前必需的商业运营范围；先验证清点价值，再按阶段投入，不提前建设复杂运营平台。

| 工作包 | 任务 | 净人日 | 结果 |
| --- | --- | ---: | --- |
| 商业规则与成本冻结 | K01 | 1 | 报价、额度、到期、支持、财务期限有依据 |
| 数据生命周期补齐 | K02 | 2.5 | 导出、注销、资产全版本清理与恢复重放 |
| 平台身份与最小后台 | K03、K04 | 4.5 | 独立平台身份、门店管理、受审计命令 |
| 任务诊断与服务记录 | K05 | 2 | 故障定位、授权诊断与处理闭环 |
| 人工核款、权益和店主界面 | K06、K07 | 3 | 重复核款不重复开通，到期操作明确 |

商业增量共**23人日，约4～5周**；与原47人日合计**70人日，约14～16周**日历窗口。仍以同一名熟练开发为前提，样本／标注、门店观察与外部审批等待另计。19人日是当前范围的估算，并非已完成或固定交付承诺；G3、K01后依据代码现状和实际资源重估。

G6允许进入受控付费前，必须有：G5结果；D07～D10已冻结；真实核款来源；服务权益／用量与数据操作验收；数据库和图片的恢复实录；明确支持与退出流程。K10只计开发／培训／移交投入，一整个续费周期的经营观察另排日历时间，不以1.5人日宣称已验证续费。

在线支付为可选独立阶段：PAY01支付创建／回调／查单3人日，PAY02退款／对账3人日，PAY03异常回归与发布核验3人日，合计**9＋3缓冲=12人日，约2～3周**，不含商户开通和审核等待。接入资格与购买入口规则未核验时不启动；G7通过后才开放相应购买流程。人工核款也必须先核验收款方式与约定，不能绕过服务发布要求。

当前HTML尚未覆盖商业后台和付费界面。K01／K04／K07应先补齐同一套HTML的对应交互评审，再实现业务；本次商业增量估算已包含这些必要页面设计和走查，不重复计算基础清点原型。
