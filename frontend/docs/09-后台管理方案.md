# 数得快：后台管理方案

补充稿 v0.3｜2026-10-16｜待评审，尚未实现｜[入口](../README.md)

## 1. 两种管理端

**门店端**继续使用小程序：店主管理本店价格、成员、记录、服务期限／用量和导出。店员负责清点与复核，无需接触套餐或平台故障报表。

**平台端**是数得快内部使用的桌面Web后台：管理多家独立门店的开通、服务权益、任务故障、成本与服务请求。门店店主不是平台管理员。平台有权看运营汇总，不自动意味着员工可以任意浏览门店照片。

受控POC用已有日志、查询和受审计的维护命令即可；开始面向多家门店收费前建设下述最小后台。连锁总部、多级加盟组织、独立商家PC端暂不做。

## 2. 最小页面与信息

| 页面 | 主要字段 | 必需动作 |
| --- | --- | --- |
| 运行概览 | 活跃门店、任务失败／排队、worker状态、容量和成本趋势；带时间范围 | 查看异常列表，按门店暂停新识别 |
| 门店列表／详情 | 门店ID、状态、店主、版本、试用／付费期限、用量、最近使用 | 开通／停用服务、查看成员与服务记录；门店名称不能作为唯一身份 |
| 任务诊断 | attempt_id、版本、耗时、失败码、是否应用、计量状态 | 定位失败；经授权发起诊断副本，不覆盖业务结果 |
| 服务订单／权益 | 套餐快照、金额、核款依据、权益期间、开通／撤销来源 | 人工核款、幂等开通、延期／撤销、退款登记 |
| 服务请求／数据请求 | 门店、问题、授权范围、责任人、状态、导出／删除结果 | 受理、处理、关闭；导出短期下载，删除有执行记录 |
| 操作审计 | 人、时间、门店、动作、原因、关联服务单、前后状态 | 只读检索；不能从后台修改审计 |

服务请求先采用普通列表和详情，状态为 OPEN／IN_PROGRESS／RESOLVED；不做工单流转引擎。运行概览展示的线上错误不是人工真值，不能直接得出识别准确率。

## 3. 权限与操作边界

首版建议只有一个平台管理员角色，账号逐人分配，不共享账号；避免为少量内部人员搭通用RBAC平台。服务核款、图片诊断、数据导出／删除采用独立操作权限，并在每次动作校验；运营人数增加后再细分客服、财务、技术角色。

| 动作 | 门店店主 | 门店店员 | 平台获授权人员 |
| --- | --- | --- | --- |
| 本店价格／成员 | 可管理 | 查看必要信息 | 协助定位，不代改门店业务配置 |
| 清点记录更正 | 按01创建关联更正 | 请求店主 | 无直接改完成快照权限 |
| 套餐购买／续费 | 可发起 | 查看必要到期提示 | 核实后开通／处理 |
| 任务统计、失败码 | 本店必要信息 | 本单必要信息 | 可查跨店运营元数据 |
| 原图／诊断输出 | 本店有权记录 | 按成员访问规则 | 服务单授权、用途与期限校验通过后短期访问 |
| 数据导出／删除 | 可发起并确认范围 | 无门店级权限 | 处理获授权请求，不可任意批量导出 |

技术运维接触生产数据同样受限，不能用“管理员”绕过用途、门店和审计。模型原始输出可能含图片信息，按证据数据控制，不能当普通日志开放给运营。

## 4. 关键操作流程

**核款开通**：核对门店ID和服务订单 → 在实际收款来源核实 → 写金额／渠道交易或凭证引用／操作者 → 同事务记核款结果和权益发放 → 再次执行返回相同发放结果。截图只是辅助材料，不能单独证明到账。

**延期／赠送**：选择门店与期限 → 展示旧、新到期时间及原因 → 独立记录人工授予，不伪装为已付费订单 → 更新权益版本。取消或退款采用关联撤销，不删除原记录。

**问题照片诊断**：店主授权特定批次和时间 → 后台申请短期读取 → 记录访问 → 到期撤销。重新跑模型生成诊断副本，默认不计门店用量，也不改已确认批次；真要更正仍由门店按01执行。

**暂停自动识别**：选择门店或全局 → 原因、影响和生效范围明确 → 停止接受新任务；已接受任务按明确取消／完成策略处理，不能静默丢失。安全停用与服务到期是不同原因，不能混用。

**导出／删除**：按11执行。删除展示门店、范围和不可恢复影响，校验授权后排队处理；商业费用凭据等单列保留记录，不悄悄承诺“所有数据立即彻底删除”。

**店主变更／账号无法使用**：正常转交由当前店主发起、目标有效成员接受，原子变更唯一店主并写审计；未完成单仍走经办交接。账号无法使用时走人工恢复服务单，核验门店权属、限制操作范围并保留依据，不能仅凭聊天截图直接把门店转给新账号。门店出售或换主体不自动继承原服务合同、财务凭据和训练授权，负责人先核实适用规则再处理。

门店侧计划接口为 `POST /v1/store/ownership-transfers` 与 `POST /v1/store/ownership-transfers/{id}/accept`；转交有期限、目标身份与expected_version，同一门店仅一个有效转交，接受与唯一店主变更同事务完成。恢复操作通过受限服务单命令，不设置任意“修改owner_id”字段接口。

## 5. 与原架构的关系

在原FastAPI模块化单体中增加 `platform_admin`、`entitlements`、`service_billing`、`data_requests`，共用PostgreSQL，不拆收费微服务。

平台Web建议 TypeScript + 简单组件库，位于计划路径 `apps/admin/`；具体框架在K03冻结，优先复用团队熟悉的工具。平台API使用 `/platform/v1` 前缀，独立平台身份、短期会话及安全登录方式；门店微信token不能访问。平台账号接入现有受控身份提供方优先，不自研复杂账户体系。

| 计划接口 | 主要规则 |
| --- | --- |
| GET /platform/v1/stores；GET /platform/v1/stores/{id} | 游标分页、筛选、最小必要字段 |
| GET /platform/v1/attempts | 跨店元数据；图片、原始输出不随列表返回 |
| POST /platform/v1/stores/{id}/service-actions | 开通／延期／暂停；原因、幂等键和期望版本 |
| POST /platform/v1/service-orders/{id}/verify | 核款来源、金额、渠道引用；重复核款不重复发权益 |
| GET／POST /platform/v1/support-cases | 简单服务记录、限定门店及授权范围 |
| POST /platform/v1/support-cases/{id}/media-access | 短期、特定图片、服务单授权；记录访问 |
| GET /platform/v1/data-requests；POST /platform/v1/data-requests/{id}/actions | 处理导出／删除，不直接修改数据库字段 |
| GET /platform/v1/audit-events | 只读、可追踪操作者与原因 |

商业数据表：`platform_members`、`support_cases`、`service_orders`、`service_periods`、`service_grants`、`usage_units`、`usage_adjustments`、`data_requests`，按阶段创建；支付回调等表只在在线支付阶段增加。平台审计可复用追加事件结构，actor_type区分门店与平台身份。

## 6. 不做什么与验收

首版不做大屏、营销活动、渠道佣金、自动销售跟进、多级审批、任意SQL执行、冒充用户登录、后台任意改账。每项可写操作必须是有输入校验、权限、幂等、版本和审计的业务命令。

收费前验收：门店token不能访问后台；未获授权不能读取原图；相同核款只发一次权益；旧版本延期不能覆盖新决定；停服务不损坏清点完成记录；所有写动作有操作者和原因；导出链接到期失效。用例与任务见05的K系列。
