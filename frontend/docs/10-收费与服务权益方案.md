# 数得快：收费与服务权益方案

补充稿 v0.3｜2026-10-16｜定价假设，尚未收费｜[入口](../README.md)

## 1. 收什么费用

软件向门店收费，建议按 **每店每月订阅，包含明确的自动识别额度** 起步，同店成员共享额度。会员人数和设备数作为容量／安全限制，不按店员人数重复收费；不按竹签根数抽成，不介入顾客餐费。

| 方式 | 优点与问题 | 建议 |
| --- | --- | --- |
| 每店订阅＋包含额度 | 门店预算可预期；能覆盖持续服务，需明确公平用量 | 推荐先验证 |
| 纯按识别次数 | 成本直接，但重拍／失败会让用户担心多花钱 | 暂不作为默认 |
| 按店员人数 | 简单，但会惩罚轮班与正常协作 | 不采用 |
| 终身买断／无限识别 | 难覆盖长期GPU、存储与支持成本 | 不承诺 |

首批建议只有一个正式基础套餐，不预先设计多层复杂权益、积分、钱包、代金券或自动续费。

## 2. 可用于验证的报价卡

以下是内部验证候选，不是市场调查结果、云服务报价或已批准对外价格：

| 项目 | 建议假设 |
| --- | --- |
| 试用 | 每店14个自然日，示例额度300个成功识别单元；一次正常试用，重复注册另作风控 |
| 基础套餐候选 | 199元／店／服务月，示例包含3000个成功识别单元；先验证真实用量分布与单位成本 |
| 超额 | 先提醒并人工扩容或补充服务权益；不默认自动扣费 |
| 年付 | 有至少一轮付费与续费证据后再定，不提前承诺折扣 |
| 额外存储／连锁 | 收集需求后独立定价，首批不做 |

199元与3000额度均可被成本或访谈结果推翻。实际对外报价前，冻结价格、税费／票据口径、服务周期、超额、到期、退款与故障补偿规则。不要通过缩短证据保留或隐藏排队来补贴低价套餐。

“服务月”按门店时区的自然月周期滚动，例如10月16日12:00至11月16日12:00；不足对应日取该月末，存储UTC时间，展示精确到期时间。提前续费从当前到期继续追加周期，过期续费从确认开通时间起算；具体规则写入服务订单快照，不按界面文案临时解释。

连续服务保留最初的日／时锚点，避免1月31日→2月末后再续成3月28日；该例下一完整周期边界应回到3月31日。过期后重新开通才建立新锚点。区间统一左闭右开，边界时刻只属于一个期间，试用转付费与赠送延期按快照明确衔接，不出现重叠额度池。

## 3. 定价必须经过两道验证

**价值上限**：每月节省工时 = 有效清点桌数 × 每桌实测节省秒数 ÷ 3600。节省工时×门店认可的工时价值，加上门店认可的可追溯收益，才能讨论愿付价格；不把未经证明的少漏收费当作收入承诺。

**成本下限**：单店成本 = 月固定基础设施费F／有效付费店数N + 该店增量请求、带宽、存储成本 + 支持、退款等分摊。GPU已计入F时，不能再把同一GPU费用完整重复算进每次成本。

内部测算售价下限 P = 单店成本／(1－目标贡献率)。贡献率只是经营分析参数，不等同净利率；研发、获客、税费等是否计入必须一致说明。

纯假设示例：F=3000元，N=50，增量8元、支持20元，则单店成本88元；售价199元对应贡献约55.8%。同样F但仅10店，单店成本328元，199元即不足覆盖。这个例子没有真实GPU报价，只用于说明不能脱离利用率拍定价格。

T19记录的真实推理、重试与峰值数据、11的存储账和08的支持工时共同用于核算；同时记录实际到账，不只看套餐标价。

## 4. 什么计入额度

计量的是软件服务使用，独立于 `count_orders` 的签数／签费。建议定义：**一个识别单元是某次提交照片的逻辑识别请求，成功得到可复核结果并应用到当前修订后计1次**。

| 情况 | 门店额度 |
| --- | --- |
| 首次有效自动结果已应用 | 计1；之后人工补／删点不再计 |
| 幂等重发、系统自动重试、同图同逻辑请求重试 | 同一单元最多计1 |
| 系统失败、超时、拒识、过时结果未应用 | 不计；仍记录实际算力成本 |
| 用户取消且结果尚未应用 | 释放预占，不计 |
| 已应用结果后用户不采用／转人工 | 已提供服务的单元保留；产品错误争议通过关联补回记录处理 |
| 重拍新照片或新增下一把，成功应用 | 新单元；提交前可见额度规则，不按每根签收费 |
| 纯人工录入、查询、确认、改组、更正记录 | 不消耗识别额度 |
| 平台诊断重跑 | 不计门店额度，独立记录运营成本 |

`usage_units` 保存 store_id、period_id、logical_request_id、状态、attempt关联、消耗／补回来源；逻辑请求ID幂等，数据库唯一约束防重复。它不是图片哈希，也不是batch_id：同批重拍新照片可产生新单元，同图重试沿用原单元。

额度状态 RESERVED → CONSUMED／RELEASED。接受任务时短事务预占，应用结果与扣减在同事务完成；重试不再次预占。实例、修订或租约已过时不能扣减。崩溃后核对任务和预占，不能因进程重启丢额度或长期占住额度。账本追加补回，不删除原消费。

自动重试期间保留同一预占；最终失败才释放。释放后用户明确重试同一逻辑请求时，先重新校验权益并原子重获预占，不能直接从RELEASED扣减；已成功应用的请求重放只返回原结果。期间行锁与唯一逻辑请求约束保证额度不会超领。

在额度跨期或到期前已接受的任务，结算回原 period_id；已预占任务不因新周期／到期二次拒绝。并发最后一个额度只能预占一次。非计费的失败也受原任务排队与防滥用限制，免费失败不等于无限占用GPU。

## 5. 服务期限与用户体验

权益状态与门店成员状态分开：TRIAL／ACTIVE／EXPIRED；人工暂停以独立SUSPENDED原因覆盖，避免把服务到期说成账号异常。

- 店主在门店页看套餐、精确到期时间、已用／预占／剩余额度和服务记录；店员只看当前操作相关提示。
- 额度80%／95%提醒店主是初始建议；不反复打断拍摄，不自动购买补充包。
- 到期或额度不足暂停接受**新的自动识别**；已接受任务按原权益交付，现有清点单可人工核实、确认和完成，不能在最后一步索费。
- 到期仍可在各数据保留期限内查询／导出；默认不再新建云端清点单。现有草稿允许人工收尾，不因付费状态删单；不承诺无限期免费云端建单或保存。
- 仅额度用尽、服务仍有效时，可继续新建人工清点单；服务到期则按上一条限制新建云端单，两种原因的提示不可混用。人工安全暂停须区分只停自动推理或禁止新写入，不撤销历史读取和允许范围内的导出。
- 续费不恢复已经按明示期限清理的图片；页面必须说明。
- 若付费和权益状态不同步，显示“开通核实中”并查单，不能引导用户重复付款。

## 6. 最小收款路径

**O1人工核款**：创建 `service_order`，快照门店、套餐版本、金额分、周期和额度 → 使用双方确认的收款方式 → 平台核实实际到账 → 同事务标记核款并发放唯一 `service_grant` → 店主查看权益。凭证引用保留，截图不独立证明到账。

未付款取消订单不撤销已有服务；单笔退款按公示规则处理实际收款，登记关联退款与权益调整。未核实退款到账不得显示退款已完成；原服务单、原授予均保留，调整采用追加记录。

**O2在线支付**：接入资格和入口规则核验通过后，增加支付回调、查单、退款与对账。前端“支付成功”不直接发权益，服务端验签／核对商户、订单、金额、币种与状态；状态不明主动查单，同一渠道交易和服务订单只能发放一次权益。微信官方要求结合回调与查单处理结果，不能只依赖客户端返回。[官方V3回调与查单指引](https://pay.wechatpay.cn/doc/v3/merchant/4012075249)

本项目尚未核验具体收款主体与服务在各终端的购买入口规则，因此不承诺微信支付或小程序内购买一定可直接接入；在线支付任务不包含在原39人日或K系列中。

## 7. 数据与接口边界

新增 `service_orders`（套餐和服务报价快照）、`service_periods`（明确起止／锚点／状态的额度期间）、`service_grants`（关联期间的额度授予／延期／撤销来源）、`usage_units`（每逻辑请求的预占／消耗状态）、`usage_adjustments`（关联原消费的追加补回）。期间额度来自有效授予与调整，事务锁定期间并校验版本；缓存计数需可从这些记录重算。先使用一个版本化套餐配置，不建设商品中心。

`GET /v1/store/service` 返回当前权益与用量；`POST /v1/service-orders` 仅店主发起；后台核款见09。创建识别任务需同时检查身份、经办、门店状态、服务权益和排队限制，任何收费限制都不能覆盖01原有的数据正确性规则。

财务凭据／退款／票据的保留期限单独冻结，不直接使用清点记录90天的规则。收费前责任人核实适用要求和服务约定，未冻结不开放正式收费。

## 8. 上线前必须验证

报价与成本有实测；扣额边界对门店可理解；重复／乱序通知不重复开通；到期前接受的任务可交付；退款／延期有来源；并发预占、跨期、崩溃回收可对账；到期不阻止当前单人工完成；服务订单不能改签费账。
