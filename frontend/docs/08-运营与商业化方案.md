# 数得快：运营与商业化方案

补充稿 v0.3｜2026-10-16｜设计建议，未开始运营｜[入口](../README.md)

## 1. 本次补充与前版缺口

v0.2 主要证明“店员能否更快、更可靠地完成一桌清点”。已有门店价格、成员、日志、试点与存储基础，但尚未形成获客、开通、服务、付费、续费和退出的闭环。不能将原来的39人日理解为完整商业化平台的工期。

用户已于2026-10-16确认：**面向多家独立门店收费**。按多门店软件服务规划运营、平台后台和收费权益；不同门店的成员、价格、清点记录、图片和服务权益相互隔离。每店订阅、具体价格／额度、试用和收款方式仍是待验证方案。

服务费指门店向数得快支付的软件费用；签费指顾客向门店支付的串签费用。二者使用不同订单、价格与状态，数得快首版仍不代门店收顾客餐费。

## 2. 第一性原理与经营目标

| 基础事实 | 运营决策 |
| --- | --- |
| 门店购买的是省时、少争议和可追溯 | 首先证明整桌收益；不以参数量、识别次数或注册量作为价值承诺 |
| 同城门店的签型、灯光与流程仍有差异 | 先准入、试用，再承诺适用范围；不把一家店的结果推广为所有店适用 |
| 晚高峰故障会直接影响工作 | 有人工退路、明确客服入口和暂停自动识别的开关 |
| 小规模阶段支持与算力成本占比高 | 先直接服务少量门店，测真实用量与支持工时，再扩张 |
| 管理能力消耗研发时间 | 先做最小平台后台；营销自动化、代理商、佣金、多级组织后置 |

商业成功需要同时有：门店持续使用、能证明节省操作时间、愿意付费、服务后仍有正贡献利润。识别98%要求和产品验收按06执行，不能用付费意愿代替。

## 3. 分阶段运营

| 阶段 | 范围建议 | 具体动作 | 退出条件 |
| --- | --- | --- | --- |
| O0 验证 | 先1家，最多3家受控试点 | 记录签型、手机、人工基线；带教拍摄／复核；至少10个营业日观察 | G5通过；能说明不适用条件和失败处理 |
| O1 小规模付费 | 建议先5～10家，逐店开通 | 定期订阅、人工核款开通、最小后台、客服与数据退出流程 | 服务开通与撤销可追溯；至少完成一轮付费周期和续费观察 |
| O2 可重复交付 | 门店数按容量测试递增 | 固化培训、开通、收费、故障与续费流程；有需要再接在线支付 | 单店成本、峰值容量、支持负担和续费理由可解释 |

数量只是验证批次建议，不是容量承诺。上一批存在未解决的错数、错金额、跨店访问、错误开通或数据丢失时，不扩大下一批。

## 4. 获客到退出的最小流程

1. **获客**：先使用现有门店关系、实地演示和试点门店转介绍；不提前采购广告或建设分销系统。记录来源即可。
2. **适配确认**：确认签型、收费分组、单把范围、网络和手机；混组、碎签等例外处理讲清楚。
3. **试用开通**：店主确认门店身份与服务说明，设置价格、邀请店员；建议提供14个自然日试用，属于待验证运营规则。
4. **激活**：店主能设置；店员能独立完成“两把累计、重拍取消、转人工、完成、查记录”。未完成带教不算已激活。
5. **跟进**：试用第1、3、7天按需联系；只在用户授权的渠道联系，本方案不授权自动发送消息。
6. **转付费**：展示适用范围、服务期限、额度、数据期限、价格和服务方式；小规模先人工核款，不能凭收款截图直接开通。
7. **续费**：建议到期前7／3／1天在店主的门店页提醒；店员拍摄流程不反复出现购买弹窗。续费权益规则见10。
8. **退出**：提供有效期内的数据导出、停止新任务、数据清理和完成记录；不因未续费立即删除历史或承诺无限保存。

首次开通建议采用一页检查表，不建设CRM：门店、联系人授权渠道、试用起止、适用范围、培训日期、服务版本、问题和下一次跟进日期。个人联系方式只保留服务必要信息。

## 5. 运营指标与分母

| 指标 | 口径与用途 |
| --- | --- |
| 激活门店率 | 完成上述激活任务的门店／已开通门店；识别出培训与准入问题 |
| 周有效使用门店 | 一周至少完成一单有效清点的门店；试点同时看频次，避免偶发操作误判 |
| 整桌收益 | 同条件辅助清点和人工基线的耗时／最终正确性；沿用06 |
| 失败与人工兜底率 | 分母分别为已接受识别请求、清点单；拒识、取消、系统错误分开 |
| 试用转付费率 | 已转付费门店／试用已结束且已获得报价的门店；未结束试用不塞入分母 |
| 续费率 | 已续费门店／该周期实际到期门店；赠送延期、退款、关店分别记录 |
| 单店贡献 | 实收分摊－算力／基础设施分摊－支持与退款等成本；不等同净利润 |
| 支持工时 | 每店带教、排障、纠错和售后工时；不能当免费资源 |

用户改过数量不一定是模型错，可能是误点、分组或人工规则。没有核实真值的线上“未修改率”，不能宣传为准确率。

先用数据库汇总查询和人工周报，不上独立数据仓库；指标必须带时间范围、样本量、版本与门店范围。

## 6. 支持与故障处理

| 问题 | 动作 | 负责人 |
| --- | --- | --- |
| 数量／签费争议 | 店员先人工核实并使用关联更正；平台只调查，不直接改历史完成单 | 门店经办人／店主 |
| 模型或存储不可用 | 明确提示并转人工；暂停接受新自动任务，保留历史查询和当前单处理 | 开发／值班负责人 |
| 服务已付款未开通 | 查服务订单、核实到账或渠道状态；幂等补发同一笔权益 | 运营核款人 |
| 图片已过期 | 解释保留规则，提供剩余结构化记录；不声称可以找回已清理图片 | 客服 |
| 退费／关店 | 走服务订单和数据退出流程，金额／期限调整均留依据 | 服务负责人 |

小团队可由同一人兼任，但操作身份与审计仍应分开。受控试点按预约营业时段保障，实际付费前必须公开服务时间与响应承诺；人员不到位不承诺7×24小时支持。

故障沟通围绕“受影响范围、当前可用操作、恢复进展、必要补偿”；未核实前不承诺根因或恢复时间。补偿由服务负责人按已公示规则执行，不能偷偷改用量账本或清点数据。

## 7. 付费上线的额外门槛

G5之后另设商业门槛：服务收费规则与成本验证完成；店主能看期限和用量；平台可以核款开通、撤销和追踪；支持与退款有明确处理人；导出、清理、恢复演练通过；后台权限通过测试。

该门槛统一编号G6；可选自助在线支付的额外门槛为G7，定义见[06](06-测试与验收计划.md)。先证明服务可受控运行，再用一个完整周期的续费结果评价商业模式。

在线支付另外核验收款主体、接入资格、所售服务在对应入口的规则、退款和票据流程。未完成核验时只规划，不宣称已可以在小程序内购买。
