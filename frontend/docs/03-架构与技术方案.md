# 数得快：架构与技术方案

版本 v0.3｜2026-10-16｜试点主架构＋商业化扩展｜[入口](../README.md)

## 1. 架构目标与取舍

首先保证身份、批次、版本、确认和金额正确；视觉引擎只负责定位与质量反馈。以一个业务工程、一个数据库和一个模型执行进程起步。

API 与 worker 分进程运行，避免模型阻塞业务请求或随 API 进程重复加载。worker 与 API 共用业务数据定义，独立安装模型运行环境。首版不引入微服务注册、Redis、Celery、Kafka、Kubernetes、向量库或通用规则引擎。

| 层 | 选型建议 | 选择原因 |
| --- | --- | --- |
| 用户端 | 原生微信小程序 + TypeScript | 聚焦拍摄、触控、微信入口，减少跨端适配层 |
| 业务 API | Python + FastAPI + Pydantic | 与模型适配生态一致，清晰校验与 OpenAPI 契约 |
| 持久层 | PostgreSQL + SQLAlchemy + Alembic | 事务、行锁、版本检查、任务持久化 |
| 评测数据 | 原图目录 + JSONL manifest + 标注 JSON | 可检查、可版本化索引，不建设数据平台 |
| 图像处理 | Pillow；按需使用 OpenCV | 归一方向、尺寸和转换；质量判断先验证再设阈值 |
| 图片存储 | POC 本地目录；试点私有对象存储 | 限权访问、保留策略、减少 API 磁盘依赖 |
| 前期引擎 | mlx-vlm + Qwen3-VL-2B MLX 4bit | 遵循已确定路线，在可用 Apple Silicon 环境验证 |
| 上线前引擎 | VLX-Seek 1.5-10B + 候选检测器 | 遵循已确定路线，在独立 GPU 环境验证 |
| 验证 | pytest、API 集成测试、前端状态／坐标单测、真机任务测试 | 按风险覆盖，不追求形式化覆盖率 |

业务环境建议 Python 3.11、PostgreSQL 17；这是项目基线建议，不代表官方最低版本。Qwen／VLX 依赖分别用锁文件固定，版本与硬件在 T03／T18 中实测后锁定，不把“最新版本”作为可复现环境。

## 4. 数据模型

ID 使用 UUID，时间存 UTC，界面按门店时区显示。每张业务表明确 store_id，外键与查询校验门店一致性。

| 表 | 关键字段 | 约束与职责 |
| --- | --- | --- |
| users | id, wechat_openid, status | OpenID 唯一，敏感标识不写普通日志 |
| stores | id, name, timezone, retention_config | 时区初始 Asia/Shanghai，保留规则有版本 |
| memberships | store_id, user_id, role, status | 联合唯一；只有活跃成员访问门店 |
| invites | id, store_id, token_hash, expires_at, max_uses, used_count, revoked_at | 邀请值只存哈希；事务校验有效期与次数，店主可撤销 |
| price_groups | id, store_id, name, unit_price_fen, active | 单价非负整数分；停用不删除旧快照 |
| count_orders | id, store_id, table_label, assignee_id, status, version, price_snapshot, finalized_snapshot, correction_of | OPEN／FINALIZED／VOID；开单快照；完成快照不可变 |
| batches | id, order_id, version, next_revision, active_revision_id, confirmed_revision_id, deleted_at | 身份稳定；version 单调递增；每批只有一个当前修订；软删除不参与合计 |
| batch_revisions | id, batch_id, revision, state, image_id, group_id, source, auto_count, final_count, final_points, active_attempt_id, manual_reason | batch_id + revision 唯一；修订状态 DRAFT／REVIEW／CONFIRMED／ABANDONED；纯人工时图片、尝试和自动数可为空 |
| recognition_attempts | id, revision_id, image_id, engine_version, prompt_version, status, lease_token, lease_until, retry_count, result, first_outcome, timings | 持久任务与识别尝试合一；重拍新建尝试；执行重试保留首次结果 |
| media_assets | id, store_id, storage_key, sha256, width, height, transform, expires_at, status | 私有访问；坐标基准固定；哈希用于辅助排查，不等于实物身份 |
| idempotency_commands | store_id, actor_id, route, key, request_hash, response, expires_at | 组合唯一；同键同内容返回原结果，同键不同内容返回冲突 |
| audit_events | id, store_id, order_id, actor_id, action, before, after, reason, created_at | 追加记录确认、人工、替换、交接、完成、更正；不建立通用事件溯源平台 |

核心索引：订单 (store_id, created_at)、未完成订单 (store_id, status, assignee_id)、批次 (order_id)、修订 (batch_id, revision)、任务 (status, lease_until, created_at)。只增加被查询和领取实际需要的索引。

price_snapshot 包含组 ID、名称和 unit_price_fen。finalized_snapshot 包含所用 revision_id、数量、来源、图片 ID、组与单价、分组小计、总根数和 amount_fen；未配置价格时 amount_fen 为 null。

## 5. 状态与版本

~~~mermaid
stateDiagram-v2
    [*] --> OPEN
    OPEN --> FINALIZED: 所有有效批次确认 / 原子完成
    OPEN --> VOID: 明确放弃
    FINALIZED --> VOID: 关联更正单完成 / 原单作废
    VOID --> [*]
~~~

~~~mermaid
stateDiagram-v2
    [*] --> DRAFT
    DRAFT --> REVIEW: 有效识别返回 / 人工录入
    REVIEW --> REVIEW: 点位或组别修改
    REVIEW --> CONFIRMED: 确认
    DRAFT --> ABANDONED: 取消
    REVIEW --> ABANDONED: 取消
    CONFIRMED --> [*]
~~~

重拍已确认批次：追加新修订并令其 active，旧 confirmed_revision 保留。汇总只读 active 修订且状态 CONFIRMED，因此新修订未确认时旧值不计入可完成合计。取消新修订：标记 ABANDONED，将 active 指回旧 confirmed_revision，并增加 batch.version；不会回退并发版本计数。

进入重拍即创建 DRAFT，不要求先有新照片；拍摄后提交该修订的识别尝试，或直接填写人工数量转为 REVIEW。这样“暂移出旧数量”的服务端状态与页面保持一致。识别重试创建新 attempt_id，更新当前修订的 active_attempt_id；不得重新新增批次。

任务状态：QUEUED → RUNNING → SUCCEEDED／FAILED／TIMED_OUT／CANCELLED。已过时的任务仍可留存执行结果，但 applied=false，不能更新当前复核内容。

确认、换组、人工改数、取消替换等写操作携带 expected_order_version、expected_batch_version。服务端在事务内锁定订单，再锁批次，核验版本和经办人；冲突返回 409 及最新版本摘要。

## 6. 主数据流与一致性

### 6.1 拍摄到复核

1. 客户端保留本地临时图片和 command_id；创建／恢复 OPEN 订单。
2. 上传图片，服务端校验实际格式、尺寸和大小；转正方向，记录归一后坐标基准，去除无必要 EXIF 信息。
3. 在同一数据库事务中创建批次修订、recognition_attempt 与幂等结果。提交后前端轮询任务状态。
4. worker 通过短事务领取任务，分配随机 lease_token，再在事务外运行推理。
5. 完成时检查当前 lease_token、任务状态、active_attempt_id、当前 revision、批次未删除、订单 OPEN 状态；满足才应用到复核结果。
6. 客户端收到当前结果后复核；点位编辑增量提交，确认时服务端重新核对实例数与版本。

推理、图片上传和数据库事务不互相保持长锁；模型推理期间不锁订单。

纯人工路径不依赖图片或模型：以 source=manual、manual_count、reason、group_id 创建 REVIEW 修订，不创建识别任务，auto_count=null。已有识别尝试再转人工时保留图片与原结果，同时撤销旧任务的应用资格。没有自动点位时不展示“原自动数”，也不允许切回不存在的逐点结果。

### 6.2 重试与迟到

- 幂等键作用于“用户的一个业务动作”，不是任意图片内容。建议保存至少 7 天，过期清理只影响重放缓存，不删除业务记录。
- 自动基础设施重试最多 1 次，只用于可重试失败；原首次失败保留在 first_outcome，不能将重试成功计入首次准确率。
- 初始任务租约 120 秒，30 秒心跳；单次执行硬上限建议 90 秒，POC 后可调。超时状态由服务端决定，前端超时不代表后台取消成功。
- worker 主控负责心跳和截止时间；常驻模型放在可终止的子进程。达到硬超时后主控终止并重载模型进程，加载期间标记未就绪，不在事件循环里假设同步生成会自行停止。
- worker 租约过期后可领取重试；旧 worker 写回必须携带原 lease_token，因此迟到写回无效。
- 用户手动转人工、重拍或取消时推进当前版本并取消旧尝试的应用资格；取消不要求底层模型立即中断，但必须阻止旧结果覆盖。
- 前端轮询建议先 1 秒、后退避至 3 秒；离开页面停轮询，恢复页面查询当前状态。

PostgreSQL 官方说明 SKIP LOCKED 可用于队列式表的多消费者领取；本项目只在任务领取使用，不用于金额或完成事务。[SELECT 文档](https://www.postgresql.org/docs/current/sql-select.html)

### 6.3 完成与更正

完成事务：校验成员／经办人 → 锁订单 → 核验 OPEN 和 expected_version → 检查有效批次全部确认 → 用快照单价重算整数分 → 写冻结快照、审计和幂等结果 → 提交。

两个设备同时完成：只有一个生成完成快照；另一个相同命令返回原结果，不同命令收到状态冲突。完成后旧任务、改点或改组返回冲突。

更正：创建 correction_of 指向原单的 OPEN 草稿，复制原确认数据；默认沿用原单价格，若显式选择新价则记录原因。新单完成时同事务作废原单并建立替换链接。数据库保证同一有效原单仅一个更正草稿；取消草稿释放占用。原完成快照保留，历史汇总排除 VOID。

更正完成时按订单 ID 固定顺序锁原单与新单，避免交叉锁；再次核验原单仍有效。放弃更正仅将新草稿作废，不触碰原单。删除批次及撤销删除也增加订单／批次版本；只允许在 OPEN 单中恢复，存在另一个待处理批次时先处理冲突。

## 7. 识别契约与坐标

统一接口：

~~~python
class RecognitionEngine(Protocol):
    def recognize(self, request: RecognitionRequest) -> RecognitionResult: ...
~~~

RecognitionRequest：request_id、image_path（worker 内部路径）、canonical_width、canonical_height、deadline_ms、engine_config_version。模型无法读取单价或修改订单。

RecognitionResult：

~~~json
{
  "schema_version": "1",
  "engine": "qwen_mlx",
  "model_revision": "实际权重revision",
  "prompt_version": "count-endpoints-v1",
  "coordinate_space": "canonical_normalized",
  "instances": [
    {"id": "p1", "x": 0.25, "y": 0.40, "bbox": null}
  ],
  "quality": {"status": "review", "reasons": []},
  "timings_ms": {"preprocess": 0, "inference": 0, "parse": 0},
  "raw_output_ref": "内部诊断引用"
}
~~~

示例字段用于契约说明，耗时 0 不是实测值。x、y 属于 [0,1]，基于转正方向后的 canonical 图；bbox 若提供则为同基准的归一坐标 [x1,y1,x2,y2]。适配层必须记录原图→canonical→引擎输入的变换并逆映射；不得猜测坐标尺度或静默裁掉越界点。

显示采用等比 contain：scale=min(view_width/image_width, view_height/image_height)，加居中留白，再应用用户缩放和平移。触点依次逆变换后写 canonical 归一点位。设备像素比仅用于画布渲染，不重复乘入业务坐标。横图、竖图、EXIF 旋转、裁剪和相册来源均有专门测试。

非法输出、仅总数无实例、截断 JSON、越界坐标，返回可识别的结果校验失败。保留原始输出供诊断，不把错误修补为“识别成功”。去重阈值必须通过逐根匹配验证，不能以减少数量为目的随意合并邻近签头。

Qwen：固定提示、权重 revision、量化、图像参数和输出预算，先验证逐点输出是否稳定。VLX：同时记录候选召回与后续区域选择错误，不能只看总数。当前公开模型 100 区域设计的依据见下文；200 扩容另行立项评测。

VLX 最小适配路径：官方 WeDetect-Base-Uni 生成候选 → 官方 VLXSeekWorker 的检测任务选择签头区域 → 读取 result_bbox_list → 框中心转换为 canonical 点位，并保留原框。Python API 调用需要适配层显式生成候选，不能假定自动调用检测器；默认候选器是否能召回竹签端面是 T18／T19 的首要验证。计数任务只有总数而没有可解析实例时，不满足本项目的逐根复核契约。[官方推理说明](https://github.com/om-ai-lab/VLX-Seek/blob/main/docs/inference.md)

## 8. API 最小集合

统一前缀 /v1。返回 request_id；错误包含 code、message、retryable、current_version（若冲突）。写命令携带 Idempotency-Key，受版本影响的命令携带 expected_version。

| 方法与路径 | 输入／输出要点 | 主要规则 |
| --- | --- | --- |
| POST /sessions/wechat | code → 业务 token、成员信息 | 服务端交换身份，密钥不下发 |
| POST /stores；POST /memberships/join | 店名／邀请 → 门店成员 | 店主建店，邀请有期限与次数限制 |
| GET /store；PUT /price-groups | 设置与价格 | 店员只读，写入仅 OWNER |
| POST /orders | 桌号选填 → 订单、价格快照 | 同键不重复开单 |
| GET /orders?status=&cursor=&date_from=&date_to=&table= | 门店记录筛选与分页 | 服务端限定当前门店；游标排序稳定 |
| GET /orders/{id} | 订单、版本、批次和状态 | 仅本店成员 |
| PATCH /orders/{id} | 桌号／备注、expected_version | 仅 OPEN、当前经办人；不接受客户端金额 |
| POST /media | multipart 图片 → media_id、尺寸、坐标基准 | 建议 10MB、长边最大 8192px；压缩参数需评测验证 |
| GET /media/{id}/access | 图片状态、短期访问地址 | 校验门店和记录访问权；过期返回明确状态，不泄露存储 key |
| POST /orders/{id}/batches | source、group_id；自动传 media_id，人工传数量／原因 | 自动事务内建任务；纯人工无图片也可创建，不伪造自动数 |
| POST /batches/{id}/retakes | expected_version → 新 DRAFT 修订 | 进入重拍即暂移出旧值，保留旧确认版本；可转人工 |
| POST /batches/{id}/attempts | media_id、expected_version → 新尝试 | 用于重拍后的识别、同图重试；替换 active_attempt，不新增批次 |
| PATCH /batches/{id}/draft | points 或 manual_count、group_id、reason | 来源分支互斥；增加版本 |
| PATCH /batches/{id}/group | group_id、expected_version → 更新汇总 | OPEN 单内已确认批次改组，仍使用本单价格快照 |
| POST /batches/{id}/confirm | 期望版本 → 确认与汇总 | 最终数量由服务端校验 |
| POST /batches/{id}/cancel-revision | 期望版本 → 恢复／移除 | 替换取消恢复旧确认 |
| DELETE /batches/{id} | 期望版本 → 移除结果 | 实际软删除并写审计 |
| POST /batches/{id}/restore | 期望版本 → 恢复结果 | 仅 OPEN 单；恢复同一批次身份，重算合计 |
| GET /attempts/{id}；POST /attempts/{id}/cancel | 当前执行状态／取消 | 不暴露模型服务凭据 |
| POST /orders/{id}/finalize | 期望版本 → 完成快照 | 检查全部确认，原子完成 |
| POST /orders/{id}/corrections | 原单、原因、价格策略 → 更正草稿 | 仅授权用户、原单保持有效直到替换完成 |
| POST /orders/{id}/abandon | 版本、原因 → 作废草稿 | 仅 OPEN；若为更正草稿，释放占用并保持原单有效 |
| POST /orders/{id}/handoff | 目标成员、版本 → 经办人 | 当前经办人／店主可转交 |
| POST /invites；PATCH /memberships/{id} | 邀请／成员状态 | OWNER；防止移除唯一有效店主 |

上传先走 API，避免首版引入分片／直传凭证复杂度；观测到带宽瓶颈后再切对象存储直传，media_id 契约保持稳定。

业务会话建议使用有时限的签名 token，微信 session_key 留在服务端；每次请求重新核验成员有效性与经办权限。过期先重新登录再重放原幂等命令，不能把身份过期当作新开单。首版不建设独立统一身份平台。

## 9. 部署、运维与成本

POC：本地模型环境和评测脚本，不要求公网；手机试用需受控 HTTPS 测试入口。试点：API、PostgreSQL、私有图片存储及单 GPU worker，worker 可访问业务数据库与私有存储，模型端口不对公网开放。

MLX 引擎在 Apple Silicon 的独立原生环境运行；API／数据库可容器化，不能假设普通 Linux 容器可运行 MLX。VLX 优先复用官方适配宿主平台的环境，锁定镜像与权重摘要。T18 同时核验主模型、候选器、依赖的许可与部署条件，再决定试点资源。

健康检查区分 API 可用、数据库可用、worker 心跳、模型加载就绪。模型未就绪不影响历史查询；暂停新识别并显示可转人工。

初始限制建议：每用户同时 1 个识别任务，每店排队上限 5 个；超过返回 BUSY 并允许稍后重试，不让请求无限排队。D03 峰值测试后修订。

记录 request_id、store_id、order_id、batch_id、revision、attempt_id、引擎与各阶段耗时；日志不打印原图、OpenID、token 或私有下载地址。异常可按关联 ID 排查。

试点数据库每日备份；图片与数据库恢复需验证关联一致性。工程目标 RPO≤24h、RTO≤4h，正式承诺前完成恢复演练。任务重启恢复、磁盘满、对象存储失败有告警；首版使用平台基础监控和日志即可。

单次成本 = worker 固定费用／有效识别量 + API／数据库分摊 + 图片存储与带宽 + 失败重试成本。收集真实数据后报价，不以模型参数量推算单次费用。未达标时可暂停自动识别、保留查询与人工记录；发布采用镜像回滚，数据库迁移优先向前兼容并先备份。

## 10. 权限、数据与发布准备

图片私有存储、短期下载凭证、门店鉴权；图片清理任务记录执行结果，过期图片保留“已清理”元数据。训练使用单独选择、人工复核与离线流程，用户修改不会自动训练模型。

开发与试点分环境；配置密钥不进源码。部署前核验微信主体、服务类目、隐私说明、合法通信域名和 HTTPS 等发布条件。具体要求以实施时官方控制台为准，不将开发工具可运行等同于真机或审核可用。

## 12. 商业运营的分阶段扩展

用户已确认面向多家独立门店收费，本节纳入商业阶段，保留以上清点主链和模块化单体。平台Web后台调用同一API工程的 `/platform/v1`，使用独立平台身份与会话；门店token不能变成平台身份。图片诊断访问需绑定授权服务单，不因平台账号存在就自动开放。

新增模块 `platform_admin`（管理与诊断）、`entitlements`（期间／额度）、`service_billing`（服务订单／核款）、`data_requests`（导出／退出）。仍使用PostgreSQL和现有持久任务；按实际工作类型领取，推理worker只执行推理，普通维护任务由轻量独立进程运行，避免导出和清理占用模型进程。无需新增消息队列或数据库。

软件服务订单与清点签费订单分表、分接口；后台不能修改已冻结清点数或签费。识别额度预占、结果应用与消耗按10的事务规则衔接，失败仍记录真实算力成本。付费前必须完成按门店的配额与限流，不以全局平均用量承诺峰值容量。

后台结构／接口见[09](09-后台管理方案.md)，收费和权益见[10](10-收费与服务权益方案.md)，存储容量与完整生命周期见[11](11-数据存储与生命周期方案.md)。这些补充对付费场景优先于本文件的试点简述；原图片30天／记录90天仍是待确认建议。任务K01～K10单独估算，不能标记为T01～T24已涵盖。
