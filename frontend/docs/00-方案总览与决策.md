# 数得快：方案总览与决策

版本 v0.3｜2026-10-16｜待评审设计稿｜[返回入口](../README.md)

## 1. 从不可省略的事实推导方案

| 基础事实 | 推导出的设计约束 | 验证方式 |
| --- | --- | --- |
| 用户要完成可核对的整桌签费清点 | 衡量整桌耗时、数量与签费错误，包含整理、等待、重拍和修正 | 同一批实物分别进行人工清点与辅助清点 |
| 单张照片只能提供可见信息 | 模糊、出框、端面完全遮挡时引导重拍、分把或人工清点 | 故意遮挡与劣质图测试 |
| 需要解释每一根从何而来 | 自动输出必须有对应点位或框；仅返回总数不能通过定位能力验证 | 对照逐根真值标注 |
| 模型可能出错，网络也可能中断 | 保留人工兜底、草稿、重试、撤销和更正 | 故障注入与店员任务测试 |
| 多把累计是一次业务操作 | 批次身份、重拍版本、确认和完成必须有确定规则 | 并发、迟到结果、重复请求测试 |
| 价格由门店决定 | 数量识别与确定性计价分离；价格取本单快照 | 改价后旧单金额保持一致 |
| 研发资源有限、效果尚无证据 | 先验证最高风险；采用模块化单体和单推理 worker 起步 | POC 决策门槛与资源监控 |

成功定义：店员能独立完成一单，过程可恢复，结果可解释，最终签费可核对；总工作量低于人工基线。不能用识别耗时替代整桌耗时。

## 3. 首版范围

必须交付：加入门店、门店价格设置、拍照／选图、识别任务、点位复核、人工录入、多把累计、重拍替换、草稿恢复、完成清点、历史、可追溯更正、基础权限和运营诊断。

首版仅处理完整圆形竹签的可见端面。不同单价由店员先分组。断签、碎段、混组、不可见端面按门店规则人工处理。

页面展示“签费小计”“完成清点”。顾客餐费支付、菜品酒水、优惠、收银系统对接不属于本版；不显示“已收款”。软件向门店收费是独立服务流程，见10，不与签费账混合。

后续优化：至少 200 候选区域、同图多轮／切片计数、训练与专用检测器、自动组别、多店复杂管理、经营分析。必须有业务收益和评测依据才进入实施。

已选择多门店付费服务，最小平台后台、权益／用量、人工核款、运营支持、数据导出／注销及恢复重放纳入商业阶段，G5通过并补齐这些能力后进入G6；这些不在原39人日试点范围内。门店管理继续在小程序，平台管理用受限Web后台。在线支付在资格明确后再进入G7，不建设完整营销或连锁管理平台。详见[08](08-运营与商业化方案.md)、[09](09-后台管理方案.md)、[10](10-收费与服务权益方案.md)、[11](11-数据存储与生命周期方案.md)。

## 4. 路线选择

| 方案 | 结果与代价 | 决策 |
| --- | --- | --- |
| 模块化 API + 持久任务 + 独立模型进程 | 业务与模型可分别升级；基础组件较少，可承受进程重启 | 推荐 |
| 小程序直接调用模型 | 门店权限、签费与重试难以形成统一规则 | 不采用 |
| 完整微服务、Redis 队列、多模型动态路由平台 | 增加组件与运维成本，现阶段没有负载证据支持 | 暂不采用 |

业务模块集中一个 Python 工程；API 和 worker 是进程边界，不是独立业务微服务。采用 PostgreSQL 保存业务与任务；评测数据用文件清单，不建设数据平台。

## 5. 不可破坏的不变量

1. 同一批次的重拍只替换该批，不新增累计。
2. 未确认、待替换、作废批次不计入可完成合计；有未处理批次不能完成整单。
3. 自动数量来自有效实例数；人工录入有独立来源，不能伪装成模型定位结果。
4. 业务重试不重复新增批次、确认或完成记录；旧版本结果不能覆盖新版本。
5. 价格在开单时快照，金额使用整数分；客户端传来的金额不作为服务端账据。
6. 完成快照不可修改；更正采用关联新单，替换成功后原单作废，保留前后依据。
7. 所有门店数据在服务端鉴权；单单仅当前经办人可编辑，明确交接。
8. 草稿与待同步不显示成云端保存完成；无法识别时用户仍能转人工。

## 6. 验证顺序

G0 样本与真值可取得 → G1 Qwen 基线和手机交互探索 → G2 业务闭环与异常正确 → G3 VLX 环境和支持范围明确 → G4 独立测试与体验达标 → G5 门店试点通过。

已确认的商业路线：G5 → G6受控付费运营（规则、后台、核款权益、数据与支持验收）→ 可选G7自助在线支付（资格、回调／查单、退款／对账验收）。G5通过不能自动证明具备收费运营条件；商业方向确认不等于具体价格、收费方式或发布条件已通过。

Qwen 阶段不承担证明 VLX 上线达标的责任；没有真实门店样本不得将 G4／G5 标记通过。200 候选扩容不加入本轮关键路径。
